Claude Code marketplace · two plugins · ten commands

Make the requirement explicit. Then prove the code matches it.

A coding agent turns any requirement into code — including the half of it you never stated. It fills that half with plausible defaults, writes tests that assert the defaults it picked, and reports green. Prorab is a set of Claude Code commands built to break that loop.

Why it exists

A ticket is never as small as its sentence.

Here is a normal, reasonable, entirely unremarkable request. Click any phrase to see what it leaves undecided.

the ticket, exactly as it arrives“ to .”
14 decisions inside one sentence

What gets decided for you, in the time it takes to start typing code

  • everyone who can see the page gets the button
  • no rate limit, no audit entry
  • delimiter ,
  • UTF-8, no BOM
  • RFC-4180 quoting, \n line endings
  • dates and numbers exactly as the screen renders them
  • a synchronous streaming download
  • no timeout handling — it works until it doesn't
  • no row cap
  • the rows currently shown, filters applied
  • the visible columns, in screen order
  • displayed values, already formatted
  • an empty result yields a header-only file
  • headers are the UI labels, in whatever language is active

Every one of these is defensible. None of them was your decision. And the tests will be written to assert exactly these — by the same context that chose them, from the same reading, in the same session. Green does not mean right; it means self-consistent.

This is the failure Prorab is built around. Not that the agent writes bad code — modern models write decent code. That it silently converts an ambiguous requirement into a specific one, and then produces its own evidence that it was right.

The position

Two conversions, and they must not happen in the same breath.

Prorab splits the job at the point where it usually collapses. First the requirement is made explicit — with a human answering, not a model guessing. Only then is it turned into code, by a run that is measured against the requirement rather than against itself.

01 / implicit → explicit

Drive out what nobody said

/prorab:refine reads the actual code and then interrogates the idea, sorting what it finds into contradictions, gaps that decide scope, and assumptions it had to invent to make the idea look coherent. It writes no code. Anything still open when the dialogue ends is written down as [?: …] — an explicit fork, not a default — and build treats that marker as a blocker it has to ask about.

02 / explicit → matching code

Keep the correspondence provable

The dialogue ends in a numbered Definition of Done: checkable given → expected pairs whose expected values come from the requirement. Every test is derived from a numbered item, has to fail before it may pass, and is judged by a skeptic that did not write it. A green suite, on its own, closes nothing.

A DoD item looks like this — and where an exact value cannot be derived independently (ranking, aggregates, parsing, anything non-deterministic), it is replaced by a metamorphic invariant from the requirement, never by an always-true relation: 

2. given a report with 1 284 matching rows and the "Team" filter set to Platform
   → the file contains 47 data rows plus one header row
3. given the same report and a filter that matches nothing
   → the header row and no data rows                          (negative)
4. given a cell whose text contains the delimiter
   → the value is quoted, and re-parsing the file returns it unchanged   (boundary)
6. given any permutation of the input rows
   → the row count and the column set are unchanged   (metamorphic, where no literal exists)

The rule that runs through all ten commands

The expected value never comes from the code.

Chain of custody for a single expected value

Each hop has one thing it is not allowed to accept. Break any of them and the run still goes green — which is exactly why each is stated as a rule the commands enforce rather than as advice.

the requirement Your answer to a question you were made to notice. ✗ an assumption nobody stated
the DoD item Numbered, checkable, given → expected, with a negative and a boundary. ✗ an intention (“export should work”)
the assertion Written before the code and run first — a valid red is AssertionError, not an import error. ✗ a value read off the implementation
the outside-in probe Driven by a context that never opened the implementation. ✗ “it returned something and didn’t error”
And a test that cannot fail is not coverage. Every test the framework counts has been shown to go red: either it was red for the right reason before the code existed, or a plausible regression was injected into an isolated worktree — invert a condition, shift a boundary, flip a sign, delete a branch, return a constant — and the test caught it. If it didn’t, the test is fixed, not the report.

The last check

A reviewer who has read the code can’t un-read it.

/prorab:verify establishes whether the thing works for the people who meet it from outside — someone in a UI, an API client, a CLI user, a reader of an export. So the context that drives the system is kept structurally blind: it is delegated at every tier, including the cheapest, and receives a charter of surfaces and expected results and nothing else.

What the probing context is handed

the charter

surface      the report screen → the "Export CSV" control
precondition seed 1 284 rows through the project's own fixture path
action       set the Team filter to "Platform", start the export
expected     47 data rows + 1 header row              ← DoD #2
             header text equals the visible column labels
negative     a filter matching nothing → header row, no data rows
boundary     a cell containing the delimiter → quoted, re-parses intact
level        L1 — headless run; assert on role, label, text, status

never crosses over

src/reports/export.py:118   build_csv_rows()
src/reports/filters.py:44   apply_team_filter()
tests/test_export.py        the tests build just wrote
the diff                    +214 −6 across 5 files
the symbol names, the paths, the framework, the ORM

Blindness is checkable, not promised: every prober returns a declaration of the files it read, the commands it ran and the locators it used. An implementation file, a test file or the diff in that list drops the items it touched to not independently verified — never quietly to works.

A browser surface is driven headless by default. Not only because it is cheaper than a model clicking through screenshots, but because it is a stronger check: a screenshot after pressing Save shows a toast, while a script reloads the page and re-reads the resource — which is what actually proves anything was stored. Forcing a 500, a timeout or an offline state is one line there and impractical by hand, and console errors and failed requests come out for free. Pixels are reserved for genuinely perceptual cases; an interactive visual session is an escalation that has to name and log its trigger.

How you actually work with it

Two sessions, and a deliberate /clear between them.

The commands are not a pipeline you configure — they are things you type. This is the shape of an ordinary feature. 

── session 1 ────────────────────────────────────────────
/prorab:refine  add a CSV export to the reports page
   a dialogue: it reads the code, argues, asks 1–4 questions at a time
   → tasks/ideas/IDEA-csv-export.md  — scope, decisions, DoD, Code map

/clear
   not hygiene. build's DoD check has to be independent of the
   conversation that produced the DoD — and the hashed Code map is
   what keeps the fresh session from re-reading the same six files.

── session 2 ────────────────────────────────────────────
/prorab:build      → working code + tasks/IMPL-csv-export.md
/prorab:verify     → outside-in verdict + the tests nobody wrote
/prorab:announce   → a short factual message you can forward

For a two-file change where all of that costs more than the work, there is /prorab:quick: one pass, two contexts, no artifacts beyond a single short record — and the same floor, a DoD stated before editing, a red-first test, one independent verifier. It re-checks its own eligibility after reading the code and hands the task over rather than finishing a large change on a small budget.

Two tracks, one discipline

The product track proves that new behavior matches a requirement. The tech track proves that old behavior did not change — a different proof obligation, so a different executor. Pick a stage.

The optimization track

Discipline you can’t afford is discipline you won’t keep.

None of the above is the reason the framework exists — but all of it fails if a careful run costs an unbounded number of tokens. So every heavy command triages complexity from cheap signals (size, blast radius, novelty, reversibility, uncertainty) and picks a tier before it opens a single extra context.

6 / 16 contexts
spent by this command reachable only on confirmed critical risk

The count is cumulative for the whole command — the main context plus every delegated or Workflow context, retries included — and it is enforced in code, not in prose: a generated Workflow script carries the remaining allowance, counts what it schedules, and routes every launch through a wrapper that throws before exceeding it. You can pin the choice with --fast, --thorough or --tier=S|M|L; the 16-context ceiling stays absolute.

A tier bounds how many contexts open, not how full each one gets. Those are different things, and a context stuffed with material nobody reads judges worse than one given the range that matters. So a second, orthogonal limit applies at every tier: raw suite output never enters a context — it goes to a file outside the working tree and comes back as a ~40-line digest — and a delegated context returns a capsule of claims and path:line pointers, never the material itself. Compaction may shorten what failed; concealing that something failed is a false report.
What no tier can buy back. The safety floor is not part of the budget: the characterization net or baseline, the contract diff, the drift search, a DoD skeptic with a fresh context, and a sabotage-proven gate whenever one is created or changed. Tiering cuts how many lenses look at the code. It never cuts the evidence.

Install

Three lines, inside Claude Code.

Both plugins live in the same marketplace but install separately — take one track or both. There is nothing to run and nothing to configure: the commands are prompt files plus a few shared contracts. 

/plugin marketplace add aartem1/prorab
/plugin install prorab@prorab
/plugin install prorab-tech@prorab

Update later with /plugin marketplace update prorab. Developing the framework itself? Point the marketplace at a local clone: /plugin marketplace add /path/to/prorab.

Then run your first task

/prorab:refine  <describe the idea in your own words — raw and half-formed is fine>

It will paraphrase the idea back at you first, so you can see immediately whether it understood it, then show its unclarity map and start asking. It writes no code and it will not declare the idea ready — that call stays yours.

Fit

When not to use this.

The cases where it is the wrong tool, stated plainly — because a framework that only describes its own strengths is not describing anything.

portability

You need more than one coding agent

Prorab is Claude Code only — plugins, slash commands, subagents, Workflow. Nothing here moves to another agent without being rewritten. If agent portability matters more than anything else on this page, pick something portable.

artifacts

You don’t want the trail in git

Every command leaves a file under tasks/. That trail is the product — it is what lets someone reconstruct in six months what was decided and why. If you would rather keep the repo clean, you are paying the ceremony and discarding what it buys.

scale

The change really is one line

refine on a typo fix is an interrogation. quick exists for the small lane and still writes a short record. Below that, just ask the agent directly — nothing here improves a rename.

inputs

Your requirements already arrive precise

If someone else writes the spec, and it closes the negatives and the boundaries, the first conversion is already done. refine will feel like it is re-litigating settled questions, and it mostly will be.

evidence

The project has no way to run a check

The floor rests on executable evidence. With no test harness and no analyzers the commands report the gap honestly rather than invent tooling — correct behavior, and also much less value than the same commands get from a project with a suite.

expectations

You expect a smarter model

It is not one. Generation quality is whatever your model already gives you. What changes is what the model is allowed to call done, and what it may spend getting there.

Where it does pay off: an existing codebase, a requirement that can be read more than one way, and a wrong-but-green implementation that would be expensive to discover later. That is the whole target — narrower than it sounds, and very common.

What lands in your project

The commands are global. The evidence is yours.

Commands install once and update from git. Everything they write is local to the working project and worth committing — and no command commits or pushes unless you ask it to. 

tasks/
├── ideas/IDEA-<slug>.md                     # refine
├── IMPL-<slug>.md                           # build
├── quick/QUICK-<slug>.md                    # quick
├── verify/VERIFY-<slug>.md                  # verify
├── audits/AUDIT-<slug>.md                   # audit
├── audits/LINT-<slug>.md                    # lint-audit
├── IMPL-refactor-<slug>.md                  # refactor
├── IMPL-lint-<plan-slug>-batch-<id>.md      # lint-fix
├── memory/                                  # small, verified project memory
└── archive/<YYYY>/<task-slug>/              # completed, verified bundles
16absolute context ceiling, flags included
~1500tokens a delegated context may hand back
~40lines of digest per suite or analyzer run
0commits or pushes you didn’t ask for

A completed, verified bundle is archived; a blocked or partial one stays active. Archiving verifies artifact identity and links first, refuses any path outside tasks/, never overwrites an existing directory, updates the links and reports every moved file.

Reference

Which command do I need?

refine → build for anything touching an external contract, spanning layers, or readable more than one way. quick for the daily two-file change. You don’t have to guess right — each one re-checks its own fit and hands over.
