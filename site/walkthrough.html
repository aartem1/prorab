Walkthrough

Eight words in. A verified change out.

One ordinary feature request, taken all the way through — with what each command establishes, what it writes down, and what it refuses to accept along the way.

Read the panels below as reconstructions, not captured output. The feature is a made-up example — a CSV export on a reports screen — chosen because everyone has shipped one and everyone has shipped it slightly wrong; the file names and numbers are illustrative, and the blocks are condensed to the part worth showing. What is not invented is the structure: the sections of each artifact, the rules the commands apply, and what each of them declines to do.

0the request

“Add a CSV export to the reports page.”

This is how the work actually arrives — in a message, in a standup, in your own head at 23:40. It is not a bad request. It is a normal one. It also contains fourteen decisions nobody has taken yet, and an agent that starts coding will take all fourteen without telling you.

So the first command writes no code at all.

1make the requirement explicit

/prorab:refine — the argument before the code

/prorab:refine  add a CSV export to the reports page

It reads the repository’s own guidance and the relevant code first — models, endpoints, the report query, the existing screens — and only then opens its mouth. The first message is never a question. It is a paraphrase, so you can see immediately whether it understood you, followed by an unclarity map.

🟥Contradictions — where the idea disagrees with itself.
🟧Gaps — what is critically undefined: actor, trigger, boundary, data format, error behavior.
🟨Hidden assumptions — what it had to invent to make the idea look coherent.
🟦Links to existing code — which modules and entities are actually affected.
the unclarity map, first round 
🟥 "everything the user sees" (your words) vs the page's own default filter —
   the screen already hides archived rows. Which of the two is "what the user sees"?
🟧 empty result: a header-only file, a zero-byte file, or a refusal with a message?
🟧 row cap — the query can return ~2M rows; the request times out at 30s
🟨 assumed: headers are the UI column labels, in the active interface language
🟨 assumed: displayed (formatted) values, not the stored ones
🟦 reports/query.py:88 already builds the filtered rowset — reuse, don't rewrite
🟦 exports/base.py:12 has a streaming-response helper with the project's own conventions

Then it asks — one to four questions at a time, not fifteen at once, with options that are specific and mutually exclusive rather than “yes / no / maybe”. Each answer updates the map, and a new answer that changes the scope is said out loud.

a question round 
Which rows does the file contain?
  ① exactly what the active filters and sorting show   (recommended — it is
     what "export what I am looking at" means to the person clicking)
  ② every row the underlying query can return, ignoring the screen filters
  ③ ① by default, ② behind an explicit "export all" option

And when the result is empty?
  ① the header row and no data rows
  ② a refusal with a message, no file

Skepticism here has a job, and it is allowed to stop when the job is done: it serves scope and the DoD, not itself. If two rounds in a row move nothing, or you start answering “as before”, it proposes settling and writing the rest down as explicit open items. And it never declares the idea ready — that call is yours.

An unresolved fork is not quietly defaulted. It is written into the artifact as [?: …], and the next command treats that marker as a blocker it has to ask about.

## Other assumptions
- [?: is a 50 000-row cap acceptable for the first iteration, or must it stream unbounded?]

## Definition of Done
1. given the report with no filters → the file contains every row the screen shows
2. given the "Team" filter set to Platform → 47 data rows plus one header row
3. given a filter matching nothing → the header row and no data rows
4. given a cell containing the delimiter → the value is quoted and re-parses unchanged
5. given a result above the cap → the documented refusal, not a truncated file
6. given any permutation of the input rows → row count and column set unchanged
7. given the file opened as its consumer opens it → the header equals the visible labels
Look at what the DoD is not. It is not “the export works”. Every item is a pair a machine can run and a human can check, the expected value comes from the requirement rather than from whatever the code will return, and items 3–6 are the negative, the boundary and — where no literal value can be derived independently — a metamorphic invariant.

2a deliberate discontinuity

/clear — and why it isn’t just tidiness

The context that argued its way to the DoD is the worst possible judge of whether the code satisfies it: it knows what it meant. So the implementation starts in a fresh session, and the only thing that crosses the boundary is the written artifact.

This would normally mean paying for the code recon twice. It doesn’t, because the Code map above carries a git hash-object hash per file. build re-hashes those paths and spends recon only on what actually moved. 

/clear
/prorab:build
   recon reused: 6/6 hashes fresh, 0 stale

A matching hash proves a file is unchanged — not that refine read it correctly. So any map claim that drives an external-contract edit still gets its current source opened, and the map’s observed verification commands remain a hint that must be confirmed before anything is run. Contexts saved this way are banked, not respent.

3explicit requirement → matching code

/prorab:build — turnkey, with the agents checking each other

Invoking it is consent to carry the task to the end. There is no approval gate in the middle and it will not ask “shall I continue”. It stops only on a real blocker — and that [?: …] from the IDEA is one:

the one interruption 
Blocker — the IDEA leaves an open fork that decides a DoD item:
  [?: is a 50 000-row cap acceptable for the first iteration?]

  ① cap at 50 000 rows, refuse above it with a documented message
  ② no cap, stream unbounded and accept the timeout risk
  ③ cap at 50 000 but make it configurable

Everything else runs without you. It derives the project’s own verification recipe before planning — the exact supported commands for targeted tests, the suite, lint, typecheck and build, taken from repository guidance, CI and task runners rather than assumed from the language — then triages complexity, picks a tier, and fans out only as far as that tier allows: recon → plan → DAG-ordered implementation → adversarial review → verification.

The part that matters: how a test earns its place

Each task ends with checks at the level and location the repository already uses. The discipline is what stops a test from faking green:

DoD #2, written before the implementation exists 
$ make test TARGET=tests/test_export.py::test_filter_is_respected

FAILED tests/test_export.py::test_filter_is_respected
E   AssertionError: expected 47, got 0

✓ a valid red — it failed on the assertion, with the value from DoD #2.
  An ImportError or a fixture error is NOT a red: it means the test is wrong,
  and the test gets fixed before any implementation is written.

Then the code is written until that goes green — and only then. Afterwards the “tests” dimension is reviewed by a separate skeptic with a fresh context, one that did not write the code. Its input is the DoD and the test diff; it opens the implementation only to confirm a finding. Its default is inverted from the usual one:

A green tests/ does not, by itself, close a DoD item. The skeptic works a yes/no rubric per item, and any “no” is a finding: was a plausible regression injected and did the test catch it; is the expected value traceable to a named DoD item rather than to a snapshot of the code; does the real unit execute, un-mocked; are the negative and boundary present; and a grep across new and changed tests for skip, xfail, commented-out cases, assert True, tautologies, sys.exit(0), try/except without re-raise, and a hardcoded answer keyed on the test input.

The sabotage probe runs in a temporary isolated worktree containing the task’s patch — never in your working tree, and never undone with git checkout --, reset or clean. How many mutations happen is a separate dial from the context tier: economy runs none, balanced (the default) takes one representative mutation per critical cluster, thorough mutates each substantial DoD item.

Documentation is part of the change, not a follow-up

As each task lands, the documents the change made factually wrong are corrected in place: a renamed path, a changed default or flag, an example that would now behave differently. Historical documents — CHANGELOG.md, release notes, ADRs, tasks/archive/** — are never rewritten to match new code. And “nothing was affected” has to be earned by actually grepping for the symbols, paths and values the change touched: an empty result is the evidence.

4does it work for the person who uses it?

/prorab:verify — from outside the code

Everything so far was checked by contexts that could see the implementation. That is necessary and not sufficient: a check designed while looking at the code inherits the code’s assumptions and then confirms them. This command splits the roles structurally.

code-aware half

Scope, charter, coverage

The main loop derives the scope with commands rather than impressions (git status --porcelain, the branch against its base, git diff --stat), reduces it to user-visible surfaces, and fixes the oracle before anything is driven. If nothing user-visible remains, it says so and names the right instrument instead of inventing a scenario.

blind half

The probing context

Delegated at every tier, including the cheapest, because blindness cannot be self-imposed by a context that has already read the diff. It gets the charter and nothing else, and returns a declaration of every file it read, every command it ran and every locator it used.

Nothing is fixed here. The only code this command writes is test code; a confirmed defect is routed — with its reproduction — to the command that owns fixes, so that command starts red.

Two of those rows are the point of the whole command. differs is not automatically a defect: observed behavior that contradicts the requirement can mean stale code or a stale requirement, so it says which reading the evidence supports and leaves the product call to you. unverifiable is a legitimate, useful result — here the environment could not be seeded with two million rows — and it names exactly what is missing. A fabricated “works” is not a result at all, which is why a works resting on the system’s own output, on “no error”, or on a screenshot with no compared value gets downgraded rather than accepted.

The first two cost nothing: their hashes still match what build recorded, so the proof is reused rather than repeated. The budget goes to the third — DoD #7 was stated, but nothing in the suite actually asserts it, so the behavior the probe just found disagreeing with the requirement is also the one nothing would catch breaking. Note that red-first cannot apply to a test written after the fact: the behavior already exists, so a new test starts green, and the only thing that makes it worth anything is proving it can fail.

5tell people, without overclaiming

/prorab:announce — twenty seconds of someone else’s attention

Not a report and not a changelog. The recipient — product, QA, an adjacent team — should understand what shipped without opening code. “Done” is taken from what actually landed (the IMPL, the diff, the test status), never from what the IDEA intended, and every non-trivial claim is fact-checked against those sources before you see it. Unproven claims are removed or softened, not smoothed over.

6not every task is that task

The cheap lane, and the debt lanes

/prorab:quick

The two-file change

One pass, two contexts, no Workflow, no IDEA, no IMPL, nothing archived. What survives is the floor: a DoD stated in chat before any edit, a red-first test, the project’s own checks, one independent verifier, the documentation duty, and one short record under tasks/quick/. It re-checks its eligibility gate after reading the code — an external contract, more than two or three files, two incompatible readings, auth/payment/permission logic — and hands over the moment one fires, leaving a record marked escalated if it had already touched files.

prorab-tech

The inverted proof

audit → refactor for structural debt and lint-audit → lint-fix for static debt. Both executors prove the opposite thing from build: that old behavior did not change. That means a characterization net green on the OLD code before anything is touched, a contract diff, a drift search, a differential old-versus-new run — and the default inverted, so behavior counts as changed until equivalence is proven. Bugs and quirks are preserved too; a latent bug the analyzers surface is routed to the product track, not silently fixed.

/prorab:verify is not tied to any of this. It works on any scope — after build, after quick, or on a branch nobody used the framework for at all. Point it at a branch, a commit range, uncommitted, or nothing, and it derives the scope itself.

7afterwards

What is in the repository when it is over

tasks/
├── archive/2026/csv-export/
│   ├── IDEA-csv-export.md      # the decisions, and what was rejected — with reasons
│   ├── IMPL-csv-export.md      # what was built, DoD → test → how the test was proven
│   └── ANNOUNCE-csv-export.md  # only if you asked for it to be saved
├── verify/VERIFY-csv-export.md # outside-in verdicts, defects, coverage
└── memory/decisions/           # at most a couple of durable, verified lines

Six months later the interesting question is never “what does this code do” — you can read that. It is “why does it do that, and what else was considered”. That is what these files hold, and it is why they are worth committing.

Archiving only happens after a re-check of scope and every mandatory DoD item. A blocker, a partial implementation or a failed mandatory check leaves everything active, exactly where you can see it.
