Mechanics

Cost is bounded. Quality is not negotiable.

Two independent limits, a hashed handoff that stops recon being paid for twice, and a small version-controlled memory that is never allowed to outrank the code.

01

Budget tiers

The heavy commands — build, verify, audit, refactor, lint-audit, lint-fix — run a budget triage step before fanning out any agents. They estimate complexity from cheap signals (size, blast radius, novelty, reversibility, uncertainty) and pick a tier.

TierTotal contextsShape
S2No Workflow at all — the main loop is the executor and reads and runs directly.
M6The usual shape for a real feature.
L12Expandable to an absolute ceiling of 16, only for confirmed critical risk or explicit --thorough.

The count is cumulative for the whole command and includes the main context plus every delegated or Workflow context, retries included. You can pin the choice: 

/prorab:build --tier=S
/prorab:build --fast          # cheapest defensible tier
/prorab:build --thorough      # up to the ceiling
/prorab:verify --verification=economy|balanced|thorough

Enforcement is mechanical, not a promise. Every delegated context carries a turn limit (6/8/12 for S/M/L), review→fix cycles are capped at 1/2/3, and a completed round that produces no new confirmed, non-duplicate finding stops fan-out immediately. Generated Workflow scripts track their remaining allowance with a counter and a boundedAgent() wrapper; unbounded fan-out is forbidden.

What the budget never buys back. The safety floor is non-negotiable at every tier: the characterization net or baseline, the contract diff, the drift search, a DoD skeptic, and a sabotage-proven gate whenever one is created or changed. Mutation intensity is controlled separately from the tier — economy, balanced (default) or thorough — and mutations run only in temporary isolated worktrees, never in your working tree.

02

A tier bounds how many contexts open, not how full each one gets.

Those are different things, and a context stuffed with material nobody reads judges worse than one given the range that matters. So a second, orthogonal set of limits applies at every tier.

run output

Never enters a context raw

Output from a test suite or an analyzer is captured to a file outside the working tree and comes back as a ~40-line digest: the command, its exit code, its own counters, one identifying line per failure. Ten failures of one class become one example plus a count; a specific failure is grepped out of the file on disk when it needs detail. A run is judged by exit code and counters, never by an OK string.

delegated returns

Capsules, not material

A delegated context hands back one schema capsule of roughly 1500 tokens — claims plus path:line, symbol or command pointers, never file contents, a full diff or raw output. An oversized return is not forwarded verbatim into the next prompt.

main loop

Holds the plan, not the code

Above tier S the orchestrator holds the artifact, the plan, the status table, the capsules and the used/cap ledger — with two bounded exceptions the source-of-truth order requires: a named, narrow range of current source when a capsule claim drives a contract decision, and the digest of a run it ordered.

deterministic steps

Enumerable facts come from a command

git hash-object for content identity, git status --porcelain for the change set, git diff --stat for the diff class, a grep per touched symbol for documentation reach — where an empty result is the evidence that nothing was affected.

Compaction never buys silence. The exit code and the failure counts are always reported in full. Shortening what failed is allowed; concealing that something failed is a false report — and a suite that collected ~0 tests is itself a finding, not a pass.

The same principle governs the commands' own text. The shared rules live in four contracts and a command loads only the ones it can act on: project-knowledge.md is read by all ten, execution.md only by the seven that run checks, documentation-sync.md only by the four that change product code, and web-probing.md only by build, quick and verify — and only when the scope in front of them actually has a browser surface.

03

Recon is never paid for twice.

Commands run in sequence, so each stage records what the next would otherwise rediscover — and stamps it with content hashes, so the next stage can tell fresh knowledge from a confident description of code that has moved on.

HandoffWhat is carriedWhat staleness costs
refine → build The Code map: files opened with git hash-object hashes, reuse and change points, contracts at risk, conventions, declared gaps. All fresh → recon costs zero contexts. Partly fresh → recon scoped to the stale entries. No map → normal recon. Never a blocker.
audit → refactor Commit plus hashes of the target files, the tests the coverage claim rests on, and the call-site files. Re-hashed before a tier is chosen. Stale target → candidate obsolete; stale test → coverage claim void; stale call site → blast radius void.
build/quick → verify Which tests were proven able to fail and how — red-first or mutation — plus the test file's hash. Fresh entries become covered (reused); the budget goes to what nobody checked yet. A reused proof never upgrades a behavior's own verdict.
lint-audit → lint-fix The exact analyzer invocations and the gate entrypoint — deliberately not violation counts. Counts go stale the moment a batch lands and re-running an analyzer is nearly free, so gate state is read from the last completed batch artifact.

A matching hash proves only that a file is unchanged — not that a map claim is right, or that a test asserts the behavior in question. So a claim that drives an external-contract edit is still verified against current source, and saved contexts are banked, not respent.

04

Project memory that can't outrank the code.

Prorab builds a small, version-controlled memory during normal work. No init, no remember command, no background process, no external model, no vector database — the structure is created lazily under tasks/memory/. 

tasks/memory/
├── INDEX.md
├── components/
├── decisions/
├── gotchas/
└── verification/

Memory is deliberately last in the source-of-truth order:

current worktree → repository instructions/docs → tests/CI/executable evidence
  → task artifacts → memory

A material memory claim must be checked against current source before it can affect behavior, architecture, contracts, scope, DoD, implementation or verification. A conflict marks the entry updated, superseded or stale — it never overrides the code. Missing memory never breaks a command.

Captured: durable decisions, boundaries, contracts and consumers, recurring gotchas, rejected alternatives, re-verified commands. Not captured: transcripts, reasoning, temporary status, ordinary code facts, unmarked assumptions, or copies of task artifacts.

05

Documentation doesn't drift away from the code.

Every command that changes code owns the documentation that change falsifies. A stale document left behind is an incomplete change, not a follow-up — reviewers treat a contradiction between the diff and a current-state document as a finding.

KindExamplesWhat a command does
Current state
claims to describe how the project works now		 README, docs/, the spec, API and configuration references, runbooks, CLAUDE.md, docstrings, --help text Corrects exactly what the change made factually wrong — a renamed symbol or path, a changed default, flag, signature, limit or format. In place, minimally, in the document's own language.
Historical
records what happened		 CHANGELOG.md, release notes, ADRs, migration notes, tasks/archive/** Never rewritten to match new code. A new entry is added where the project's convention calls for one; a past entry stays as it was written.

Anything wider — a style rewrite, a pre-existing gap, a restructure, a correction needing a product decision — is reported with the follow-up named, not absorbed into the diff. And "nothing was affected" has to be earned by actually searching the docs for the symbols, paths and values the change touched.

/prorab:verify sits deliberately outside this duty: it changes no behavior, so it falsifies no document — and when observed behavior contradicts a document, either one of them can be the wrong one. That is a finding it reports with both readings named.

06

Artifact lifecycle

Before moving anything, a command verifies explicit artifact identity and links, refuses paths outside tasks/, never overwrites an existing directory (deterministic -2, -3 suffixes), updates links, re-opens destinations and reports every moved file. A blocker, a partial completion or a failed mandatory verification leaves artifacts active. 

tasks/archive/
└── YYYY/
    ├── <task-slug>/
    ├── refactor-<task-slug>/
    └── lint-<plan-slug>/

Archived work is never picked up as active by default. /prorab:quick and /prorab:verify archive nothing at all — they each leave exactly one record. And no command commits or pushes unless you explicitly ask.
