Mechanics

The rules that decide what may be called done.

Everything below exists to keep one property true: the expected value in every check can be traced back to a stated requirement, and never to the code that is being checked. The rest is making that affordable.

01

What “explicit” has to mean to be worth anything

A Definition of Done that reads “the export works” is not a requirement — it is the same ambiguity in a more confident font. The form is fixed, and it is fixed because each part of it closes a specific way of being wrong.

RuleThe failure it closes
Numbered, one given <input> → <expected> pair per item An intention cannot be run. A pair can, which is what makes “done” checkable rather than declared.
The expected value comes from the requirement, not from how the code returns it The central one. An expectation derived from the implementation always agrees with the implementation.
At least one negative per non-trivial item — empty or invalid input → the documented refusal Happy-path-only suites. Most real defects live in what the code does when the input is wrong.
At least one boundary — 0, the limit, off-by-one The single most common class of silent bug, and the one a golden snapshot hides best.
Where no literal value is independently derivable — a metamorphic invariant from the spec Ranking, aggregates, parsing, non-determinism. Without this rule, these get a snapshot instead. The invariant must be one the spec implies, not an always-true relation.
An unclosed fork is written as [?: …] The silent default. The marker survives into the next command, which treats it as a blocker and asks — rather than picking something reasonable and never mentioning it.

Metamorphic invariants are the part people skip, so: permuting the input does not change the total; parse ∘ serialize returns the original; running it twice is idempotent; more input never lowers the count. Each is checkable without knowing the answer, which is exactly the situation a ranking or an aggregate puts you in.

02

A test that cannot fail is not evidence.

Every test the framework counts has been shown to go red. There are exactly two ways to show it, and which one was used is recorded per test, with the test file’s hash.

route 1 · red-first

It failed before the code existed

The test is written on a DoD item and run before implementing. A valid red is an AssertionError carrying the value from the DoD. An ImportError, a syntax error or a fixture error is not a red — it means the test is wrong, and the test is fixed before any implementation is written. The actual run tail goes into the artifact.

route 2 · mutation

A regression was injected and it caught it

For a test written after the behavior already works — where red-first is impossible — one plausible regression is injected from a closed set: invert a condition, shift a boundary, flip a sign, delete a significant branch, return a constant. Red → covered. Not red → weak, however convincing the test reads, and the report says so.

Mutations never run in your working tree. A temporary isolated worktree is created, the task-scoped patch is materialized there, the regression is injected, the test is run, and the worktree is removed after confirming your tree is untouched — never git checkout --, git reset or git clean to undo a probe.

The skeptic, and its inverted default

The “tests” dimension of the review is run by a separate agent with a fresh context — not the one that wrote the code. Its input is the DoD and the test diff; it opens the implementation only to confirm a finding. Its starting position is the opposite of the usual one: a green suite does not, by itself, close a DoD item. It works a yes/no rubric, and any “no” is a finding.

The rubricWhat a “no” looks like
Sabotage probeA plausible regression was injected and no test went red.
Independent oracleA magic number with no derivation from a requirement, or a snapshot taken from the code itself.
Real unitThe unit under test — or its direct return — is mocked. Mocking external boundaries by name (network, DB, time, filesystem) is fine and expected.
Negative + boundaryMissing, with no specific reason why the behavior has none. “Not applicable” is not a reason.
No workaroundsA grep across new and changed tests hits skip, xfail, a commented-out case, assert True, a tautology, no assertion at all, sys.exit(0), try/except without re-raise, or a hardcoded answer keyed on the test input.
A caveat the framework states about itself. These are lenses for a skeptic, proven by a command’s output — not checkboxes the author awards themselves. Pushed too hard, “the reviewer must find something” breeds false findings and over-engineering, so the skeptic’s focus is DoD coverage and defused fake checks, explicitly not style.

How a run is judged

By its exit code and its own counters — never by an OK or passed string in the output. A suite reporting passed having collected approximately zero tests is a finding, not a pass. And the verification recipe itself is derived from the project — repository guidance, CI, task runners, package scripts, existing test conventions — rather than assumed from the language. A check with no discoverable command is reported as a gap; it is not invented, and no tooling is silently installed.

03

Blindness has to be structural, not promised.

Everything in section 02 is performed by contexts that can see the implementation. That is necessary and not sufficient: a check designed while looking at the code inherits the code’s assumptions and then confirms them. So /prorab:verify splits the roles physically. The probing context is delegated at every tier, S included — not because probing is expensive, but because a context that has already read the diff cannot un-read it.

the charter

What crosses over

Per behavior: the surface a consumer reaches it through, the precondition and how to obtain it via the project’s own seeding path, the action, the expected result and the requirement it comes from, a negative and a boundary case, and the allowed instruments. If an item can only be phrased in implementation terms, it is not a user-visible behavior — it is dropped, and the report says so.

the declaration

What makes it checkable

Every prober returns every file it read, every command it ran, and — for a scripted probe — every locator it used. An implementation file, a test file or the diff in that list drops the items it touched to not independently verified. Those items are re-probed within the cap or reported at that grade; they are never laundered into works.

Weak passes are downgraded rather than accepted: a works resting on the system’s own output, on “no error”, or on a screenshot with no compared value becomes unverifiable with the reason stated. A defect is reproduced a second time before being announced, so a flake is not reported as a bug. And an honest unverifiable, naming the missing environment, access, data or oracle, is a legitimate result — a fabricated “works” is not.

The instrument ladder for a browser surface

The default for a web UI is a headless run, and the reason is not only speed. In a visual session the model is the driver: look at a screenshot, decide, click, look again — every step a round trip carrying an image. In a headless run it authors the session once, executes it with one command, and judges a structured result. That is also the stronger check: a screenshot after pressing Save shows a toast, while a script reloads the page and re-reads the resource, which is what actually proves the data was stored.

LevelWhenWhat it asserts on
L0 — no browserThe behavior is observable over HTTP, the CLI, or the data it writes.A plain client. A browser is needed only when the behavior lives in the browser: client routing, client state, client validation, rendering.
L1 — headless run (the default)Anything that lives in the browser.Role and accessible name, label, visible text, URL, response status, storage, console — and layout measured: clipping as scrollWidth > clientWidth, overlap as intersecting boxes, off-screen as a box outside the viewport, plus computed size and colour.
L2 — pixels, clippedA genuinely perceptual requirement: visual regression, canvas or chart rendering, print, a deliberate aesthetic.One element-clipped screenshot taken inside the same L1 run, read only for the item that needs adjudication.
L3 — interactive visual sessionEscalation only, on a named trigger: an auth/2FA/captcha step a human must complete, a native dialog, an unreachable environment, or L1 failing twice to find a user-facing handle.The trigger is logged with the escalation. An unlogged L3 is how this quietly decays back into the slow default.

Every run captures console errors and unhandled rejections, failed requests with method, path and status, the write request’s own status behind a save rather than the message the UI shows afterwards, persistence proven by an independent re-read, and — for a negative case — the documented refusal with the failure injected (a 500, a timeout, an offline state, an empty or invalid submit) rather than waited for.

Locators are user-facing only — role plus accessible name, label, visible text, placeholder, heading, or a data-testid the project’s own conventions publish. Never a class hash, an internal id, an XPath, or a selector lifted from the source. This one rule does two jobs: authoring a script is the single moment a blind prober is tempted to open the implementation “just for a selector”, and it is also simply how a user finds a control. A handle that cannot be found by its user-facing name is therefore a finding — a labelling or accessibility gap — never a reason to read the code.

04

The tech track proves the opposite thing.

build proves that new behavior matches a requirement. refactor and lint-fix prove that old behavior did not change. That is not the same proof with a different subject — it needs a different instrument entirely, which is why they are separate executors rather than a flag on build.

the oracle

The old code is the requirement

There is no DoD to derive an expectation from — the expectation is what the code did yesterday. So a characterization net is written first, pinning the current behavior and green on the OLD code, and structure is only changed under green. No net that can catch a behavior change, and nothing to build one from, is a blocker. Bugs and quirks are preserved too: a refactoring that also fixes something is two changes wearing one diff.

the default

Changed until proven equivalent

The drift search assumes divergence and goes looking for it — boundaries, negatives, unusual types, concurrency, errors — and where it is possible, an old-versus-new differential run on common inputs compares outputs and side effects directly. Any diverging input is a critical finding. The sabotage probe here targets the net: if a mutation survives, the net is leaky and the net gets fixed, not the refactoring.

The static pair carries the same directive with one addition that matters. A strict analyzer routinely surfaces a real bug — a dead branch, an unreachable path, a swallowed exception. Fixing it would be a behavior change inside a pass that claims to make none, so it is recorded and routed to the product track, and the pass itself annotates or suppresses at the agreed bar. The gate lifecycle is stated with the same honesty: batches before the first gate are preparatory and are never described as locked; the gate batch creates the first enforcement and sabotage-proves it; later batches tighten that same gate and prove the changed coverage.

05

Two independent limits: how many contexts, and how full each one gets.

The heavy commands — build, verify, audit, refactor, lint-audit, lint-fix — run a budget triage before fanning out any agents, estimating complexity from cheap signals: size, blast radius, novelty, reversibility, uncertainty.

TierTotal contextsShape
S2No Workflow at all — the main loop is the executor and reads, edits and runs directly.
M6The usual shape for a real feature: an orchestrator plus up to five delegated contexts.
L12Expandable to an absolute ceiling of 16, only for confirmed critical risk or an explicit --thorough.

The count is cumulative for the whole command and includes the main context plus every delegated or Workflow context, retries included. Enforcement is mechanical: every delegated context carries a turn limit (6/8/12 for S/M/L), review→fix cycles are capped at 1/2/3, a completed round that produces no new confirmed non-duplicate finding stops fan-out immediately, and a generated Workflow script tracks its remaining allowance with a counter and a boundedAgent() wrapper that throws before exceeding it. Unbounded fan-out is forbidden outright.

The second axis: occupancy

A tier bounds how many contexts open, not how full each one gets — and those are different things. A context stuffed with material nobody reads judges worse than one given the range that matters, so three limits apply at every tier.

run output

Never enters a context raw

Output from a suite or an analyzer goes to a file outside the working tree and comes back as a ~40-line digest: the command, its exit code, its own counters, one identifying line per failure. Ten failures of one class become one example plus a count; a specific failure is grepped out of the file on disk when it needs detail. Compaction may never hide a result — shortening what failed is allowed, concealing that something failed is a false report.

delegated returns

Capsules, not material

A delegated context hands back one schema capsule of roughly 1500 tokens — claims plus path:line, symbol or command pointers, never file contents, a full diff or raw output. When material genuinely has to be seen, the capsule names it and the orchestrator opens that one range, so the reading happens once where it is needed. An oversized return is never forwarded verbatim into the next prompt.

main loop

Holds the plan, not the code

Above tier S the orchestrator holds the artifact, the plan, the DoD table with per-item status, the capsules and the used/cap ledger. Two bounded exceptions stand, because the source-of-truth order outranks tidiness: a named, narrow range of current source when a capsule claim materially drives a contract decision, and the digest of a run it ordered. Needing broad reading up here is a signal the work was under-delegated.

deterministic steps

Enumerable facts come from a command

git hash-object for content identity, git status --porcelain for the change set, git diff --stat for the diff class, and a grep per touched symbol for documentation reach — where an empty result is the evidence that nothing was affected. Cheap, exact, repeatable, and stronger than an impression.

The same principle, applied to the commands’ own text

The shared rules live in four contracts, and a command loads only the ones it can act on. A read-only command has no business paying for the executor rules, and a change with no browser surface never pays for the web method.

verify runs checks and writes tests, but changes no behavior — so it falsifies no document and carries no documentation duty. The tech track has no web contract at all: its oracle is old-versus-new behavior, which needs a differential run, not a consumer session.

What no tier buys back. The safety floor is outside the budget at every tier: the characterization net or baseline, the contract diff, the drift search, a DoD skeptic with a fresh context, and a sabotage-proven gate whenever one is created or changed. Mutation intensity is a separate dial — economy (none), balanced (one per critical cluster, the default), thorough (one per substantial boundary). Tiering cuts how many lenses look at the code; it never cuts the evidence.

06

Nothing is paid for twice.

The commands run in sequence, and each stage already knows something the next would otherwise rediscover. So each records it — stamped with content hashes, so the next stage can tell fresh knowledge from a confident description of code that has moved on.

HandoffWhat is carriedWhat staleness costs
refine → build The Code map: files opened with git hash-object hashes, reuse and change points, contracts at risk, conventions, declared gaps. All fresh → recon costs zero contexts. Partly fresh → recon scoped to the stale entries plus the declared gaps. No map → normal recon. Never a blocker.
audit → refactor Commit plus hashes of the target files, the tests the coverage claim rests on, and the call-site files. Re-hashed before a tier is chosen, since safety and blast radius are inherited from it. Stale target → candidate obsolete; stale test → coverage claim void; stale call site → blast radius void.
build/quick → verify Which tests were proven able to fail and how — red-first or mutation — plus the test file’s hash. Fresh entries become covered (reused), and the budget goes to what nobody checked yet. A reused proof never upgrades a behavior’s own verdict.
build/quick → verify (web) The runner and its exact invocation, the base URL that worked, the seeding path, the recorded answer to any provisioning question. A stale entry means the recipe is re-derived. A runner that fails on first use is re-derived, not retried blindly.
lint-audit → lint-fix The exact analyzer invocations and the gate entrypoint — deliberately not violation counts. Counts go stale the moment a batch lands and re-running an analyzer is nearly free, so gate state is read from the last completed batch artifact instead.

Two bounds hold on every one of these. A matching hash proves a file is unchanged — not that the claim about it is right, and not that a test asserts the behavior in question; so a claim that drives an external-contract edit is still verified against current source. And saved contexts are banked, not respent: a cheap recon is not a licence to fan out further.

07

Documentation doesn’t drift away from the code.

Every command that changes code owns the documentation that change falsifies. A stale document left behind is an incomplete change, not a follow-up — it is part of the command’s own completion condition, and reviewers treat a contradiction between the diff and a current-state document as a finding.

KindExamplesWhat a command does
Current state
claims to describe how the project works now		 README, docs/, the spec, API and configuration references, runbooks, CLAUDE.md and other agent guidance, docstrings, comments, --help text, and the examples inside any of them Corrects exactly what the change made factually wrong — a renamed symbol or path, a changed default, flag, signature, limit, format or command, an example that would now behave differently. In place, minimally, in the document’s own language and style.
Historical
records what happened		 CHANGELOG.md, release notes, ADRs, migration notes, tasks/archive/**, completed task artifacts Never rewritten to match new code. A new entry is added where the project’s convention calls for one; a past entry stays exactly as it was written.

What keeps this from becoming an endless documentation project is the scope rule: the duty is what the change made factually wrong. Anything wider — a style rewrite, a gap that predates the change, a restructure, a correction needing a product decision, or a fix larger than the code change itself — is reported with the follow-up named, not absorbed into the diff. And “nothing was affected” has to be earned by actually grepping for the symbols, paths, flags and literal values the change touched.

/prorab:verify sits deliberately outside this duty. It changes no behavior, so it falsifies no document — and when observed behavior contradicts a document, either one of them can be the wrong one. That is a finding it reports with both readings named, never a document it quietly rewrites.

08

Project memory that can’t outrank the code.

Prorab accumulates a small, version-controlled memory during normal work. No init, no remember command, no background process, no external model, no vector database — the structure is created lazily under tasks/memory/, and every command still works when it is absent. 

tasks/memory/
├── INDEX.md          # one line per entry: link, type, status, topic, key paths
├── components/       # component, contract, pattern
├── decisions/
├── gotchas/
└── verification/     # commands that were actually re-verified

Memory is deliberately last in the source-of-truth order:

current worktree → repository instructions and docs → tests, CI and other
  executable evidence → task artifacts → memory

Memory accelerates discovery; it never proves current behavior by itself. A material claim that affects behavior, architecture, an external contract, scope, DoD, an implementation choice or the verification recipe must have its current source opened before it can be used. On a conflict the current evidence wins and the entry is updated, marked superseded or marked stale — an entry never overrides the code.

Captured: durable architectural decisions, component responsibility, contracts and their consumers, non-obvious constraints, recurring gotchas, verified commands, rejected alternatives and why. Not captured: transcripts, reasoning, temporary status, one-off errors, ordinary code facts that are cheaper to read directly, unmarked assumptions, or copies of task artifacts. Usually zero to three entries per task are enough.

09

Artifact lifecycle

A bundle is archived only after the command has re-checked scope and every mandatory DoD item and recorded a successful final status. A blocker, a partial completion or a failed mandatory check leaves everything active. 

tasks/archive/
└── YYYY/
    ├── <task-slug>/
    ├── refactor-<task-slug>/
    └── lint-<plan-slug>/

Before moving anything, a command verifies explicit artifact identity and cross-links — a similar slug alone is not enough — refuses paths outside tasks/, path traversal and unexpanded globs, never overwrites an existing directory (deterministic -2, -3 suffixes), updates the links in the moved bundle and the remaining artifacts, re-opens each destination and reports every moved file. No recursive deletion, no broad destructive shell operations.

Archived work is never picked up as active by default: a lookup searches the archive only when you name an archived task explicitly, when announce needs completed work, or when a historical question requires it. /prorab:quick and /prorab:verify archive nothing at all — they each leave exactly one record. And no command commits or pushes unless you ask.

How it compares

Prorab sits between a hand-written Claude Code setup and a full product-development framework. Its narrower bet: an existing codebase needs two things at once — a repeatable path from an unclear task to verified code, and a separate, behavior-preserving path for paying down debt.

A comparison of documented default workflows as of 2026-07-25, not a benchmark of model output. All of these are extensible, so “not in the default workflow” does not mean “impossible to add”. Full sources and a per-approach discussion are in the README.

Choose Prorab when auditability, behavior-preserving maintenance and a hard context boundary matter more than agent portability. Choose Superpowers for a prescriptive TDD/subagent methodology that follows you across coding tools. Choose Spec Kit when specifications are the primary organizing artifact and you want a large integration surface. Choose BMAD when the work starts before engineering — market and domain analysis, PRDs, architecture, UX — and role separation is useful. Use native Claude Code customization when the workflow is small or unusual enough that owning the policy is cheaper than adopting a framework.
